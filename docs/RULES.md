【核心开发规则】

禁止擅自删改功能
不允许未经用户授权，删除或修改 CoverPicker 已有的功能、布局、按钮等。如果确实需要更改，必须取得用户确认。如果不确定用户原来已实现什么功能，绝不允许擅自修改或生成简化的文件代码，务必向用户询问、索取原始代码。每次调试，用户都会使用你最后提供的版本完整覆盖，不需要对此提出质疑，不需要就此向用户确认。

先确认后修改
除非用户仅给出报错日志，其他时候必须向用户确认错误或问题的现象，以及用户的需求，用户同意后再开始修改代码。
例外：调试日志 —— 在排查问题时，允许直接添加 print/logger.debug() 等调试输出，无需用户确认，因为调试日志不改变程序逻辑。调试完成后应移除或注释掉这些日志。
当用户提供了截图来说明问题时，如果读不懂一定要如实告知用户，并询问详细的错误，严禁自己胡乱解读、胡乱修改。
当修改方案与用户需求完全一致时，不需要请用户确认。只有当方案与用户需求不同、或存在多种可选方案时，才需要向用户确认。

提供代码的方式

完整文件：当文件需要大范围修改（超过 20 行或涉及多个方法）时，必须提供完整文件，以便用户直接覆盖。

段落替换：当修改范围较小（不超过 20 行，且仅涉及单个方法或连续段落）时，必须以下列方式提供：

使用如下段落覆盖 xxx.py 文件中从 def method_name(...) 开始，到 return result 结束的段落：
（提供完整方法代码）

禁止：仅提供“修改以下方法”而不给出完整方法代码，或让用户自行替换。

例外：如果用户明确要求完整文件，则必须提供完整文件。

三轮自审后输出
技术审查 → 需求审查 → 规则审查，全部通过才能输出代码。
前置策略：调试版本优先
在排查复杂问题时，优先提供带调试日志的版本（调试版），而不是直接提供修复方案。调试版应包含足够的日志输出，帮助用户和助手快速定位问题。问题定位后，再提供干净的正式修复版本，并移除所有调试代码。

简洁输出
用户确认方案后，只输出“好的，我来实现：”+ 完整代码（或段落替换代码）。

更新文档
用户要求更新 PRODUCT.md 和 PROGRESS.md 时，除非用户明确表示要取消，否则不允许删除文档原有的内容，只能修改、添加内容，并且输出更新后的完整文档。
